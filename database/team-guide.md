# ใช้ฐานข้อมูลร่วมกันในทีม

ทุกคนใช้ schema.sql ชุดเดียวกันบนฐานข้อมูลพัฒนาของตัวเอง โครงสร้างเหมือนกัน แต่ข้อมูลทดลองไม่จำเป็นต้องเหมือนกัน
ส่งไฟล์นี้พร้อม schema.sql, seed.sql และ Data Dictionary ให้เพื่อนก่อนเริ่มทำ backend

| คนรับผิดชอบ | ตารางที่เขียนข้อมูล | ตารางที่ต้องอ่านร่วม |
|---|---|---|
| โอปอ | STUDENT, STUDENT_SKILL | APPLICATION, SAVED_JOB, JOB ตามฟีเจอร์ที่เชื่อม |
| มิก | EMPLOYER, JOB_CATEGORY, JOB, JOB_SKILL | APPLICATION, STUDENT, STUDENT_SKILL |
| เตอร์ | APPLICATION, SAVED_JOB | JOB, JOB_CATEGORY, JOB_SKILL, STUDENT, EMPLOYER |

หน้าพิจารณาใบสมัครของนายจ้างยังอยู่กับเตอร์ ตามแผนเดิม แม้ตารางนายจ้างจะอยู่กับมิก
การแบ่งตารางหมายถึงผู้ดูแลฟีเจอร์ ไม่ใช่การตรวจสิทธิ์ด้วยบัญชี MySQL แยกคน สิทธิ์ผู้ใช้ต้องตรวจใน backend ทุกคำขอ

## ลำดับเตรียมข้อมูลของตัวเอง
1. ทุกคนรัน schema.sql และ seed.sql ในฐานข้อมูลใหม่บนเครื่องตัวเอง
2. โอปอทำสมัครนักศึกษาและสร้างบัญชีสมมติผ่าน backend ที่ hash รหัสผ่านจริง แล้วเพิ่มทักษะ
3. มิก ทำสมัครนายจ้างและสร้างบัญชีสมมติผ่าน backend แล้วสร้างประกาศโดยเลือก category_id จาก JOB_CATEGORY และเพิ่ม JOB_SKILL
4. เตอร์ ต้องมีบัญชีนักศึกษา นายจ้าง และงาน Open บนเครื่องตัวเองก่อน จึงทดสอบ SAVED_JOB และ APPLICATION ได้
5. ทดสอบรวมตั้งแต่สมัครบัญชี ประกาศ ค้นหา สมัคร พิจารณา จนดูผล

หาก backend สมัครสมาชิกยังไม่พร้อม ให้สร้าง password_hash ด้วยไลบรารีที่ทีมเลือกแล้วค่อยเพิ่มบัญชีสมมติ ห้ามใส่รหัสผ่านตรง ๆ หรือ hash หลอก
เมื่อต้องแชร์ข้อมูลทดลอง ให้ทำไฟล์ seed แยกตามฟีเจอร์ เช่น seed-students.sql และ seed-employers.sql โดยใช้ข้อมูลสมมติทั้งหมดและระบุลำดับรัน
อย่าผูกความสัมพันธ์กับ ID ที่เดาว่าเป็น 1 ให้ใช้ LAST_INSERT_ID() หลัง INSERT ใน connection เดิม หรือค้นหาบัญชีด้วยอีเมลและประเภทงานด้วยชื่อที่ UNIQUE

## ข้อตกลง backend ก่อนแยกทำ
- ใช้ชื่อคอลัมน์และสถานะตรง Data Dictionary; ใช้ parameterized queries กับข้อมูลจากผู้ใช้
- ตอนล็อกอินแยกบทบาท student/employer เพราะอีเมลเดียวกันอาจอยู่ได้ทั้งสองตาราง
- อ่าน student_id หรือ employer_id จาก session ที่ตรวจแล้ว อย่าใช้ ID เจ้าของที่ส่งมาจากฟอร์มเป็นหลักฐานสิทธิ์
- สมัครงานครั้งแรกมี status = Pending; งานใหม่มี status = Open โดยไม่ต้องส่งค่าเอง
- เปลี่ยนสถานะใบสมัครได้เฉพาะนายจ้างเจ้าของงาน และอ่านโปรไฟล์ผู้สมัครได้เฉพาะงานของตัวเอง
- ตกลงเพิ่มว่ากลับไปสถานะก่อนหน้าหรือเปิดงานใหม่ได้หรือไม่ก่อนทำฟีเจอร์นั้น
- UNIQUE ของ APPLICATION กันสมัครซ้ำ แม้มีคำขอพร้อมกัน; backend ต้องแปลง duplicate-key error เป็นข้อความที่เข้าใจได้
- SAVED_JOB และตารางทักษะใช้ composite PK กันข้อมูลซ้ำ; ยกเลิกบันทึกงานลบเฉพาะแถว SAVED_JOB

## สมัครงานโดยไม่ชนกับคำขอปิดงาน
ใช้ transaction และล็อกแถว JOB ใน connection เดียวกัน เพื่อไม่ให้ตรวจ Open แล้วมีคำขออื่นปิดงานก่อน INSERT:

```sql
START TRANSACTION;
SELECT job_id, status FROM JOB WHERE job_id = ? FOR UPDATE;
-- Backend: ถ้าไม่พบงานหรือ status ไม่ใช่ Open ให้ ROLLBACK และหยุด
INSERT INTO APPLICATION (student_id, job_id) VALUES (?, ?);
COMMIT;
```

เครื่องหมาย `?` เป็น placeholder สำหรับ driver ของ backend ไม่ใช่ SQL ที่วางใน Workbench แล้วรันได้ตรง ๆ
ถ้า INSERT ล้มเหลวต้อง ROLLBACK; ปิดงานด้วย UPDATE JOB ใน transaction โดยตรวจ employer_id จาก session
InnoDB จะล็อกแถวเดียวกันระหว่าง UPDATE และ FOR UPDATE ทำให้ผลลัพธ์ขึ้นกับ transaction ที่ได้ล็อกก่อน
อย่าล็อกค้างระหว่างรอให้ผู้ใช้กดยืนยัน และอย่าใช้ transaction คนละ connection

## ตรวจหลังติดตั้ง
รัน verify.sql: ต้องพบ 8 ตาราง, 8 FK แบบ RESTRICT, 16 CHECK ที่ ENFORCED = YES และประเภทงานเริ่มต้น 7 รายการ
จากนั้นทดสอบผ่าน backend ด้วยข้อมูลสมมติ:

| ทดลอง | ผลที่ต้องได้ |
|---|---|
| สร้างบัญชีภาษาไทยและเพิ่มงานที่ข้อมูลครบ | บันทึกได้ ชื่อภาษาไทยอ่านกลับได้ |
| สมัครและบันทึกงาน Open ครั้งแรก | บันทึกได้ เวลาเป็น UTC และใบสมัครเป็น Pending |
| สมัครหรือบันทึกงานเดิมซ้ำ | ถูกปฏิเสธด้วย UNIQUE/PK |
| ใส่ student_id/job_id ที่ไม่มีอยู่ | ถูกปฏิเสธด้วย FK |
| ค่าจ้างติดลบ หรือ status ไม่อยู่ในชุดที่กำหนด | ถูกปฏิเสธด้วย CHECK |
| ลบงานที่มีใบสมัคร | ถูกปฏิเสธด้วย FK; ปิดงานแทนและประวัติยังอยู่ |
| สมัครงาน Closed | backend ปฏิเสธ แม้ SQL schema ไม่ตรวจข้ามตาราง |
| ผู้ใช้แก้ ID เพื่อดูหรือแก้ข้อมูลของคนอื่น | backend ปฏิเสธ |

## เปลี่ยนโครงสร้างหลังเริ่มใช้
ตกลงร่วมกันก่อนเปลี่ยนชื่อ/ชนิด/NULL ของคอลัมน์ จากนั้นเพิ่มไฟล์ migration ที่มีเลขลำดับและคำอธิบายวิธีรัน
ทุกคนรัน migration เดียวกันตามลำดับ อย่าแก้ schema.sql แล้วลบสร้างฐานข้อมูลที่มีข้อมูลเพื่ออัปเดต
ยังไม่ได้เลือกผู้ดูแล schema กลางในทีม ให้กำหนดก่อนรวมการเปลี่ยนโครงสร้างครั้งแรก
